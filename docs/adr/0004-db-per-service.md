# ADR-004: Своя PostgreSQL на каждый сервис (To-Be)

- Status: Accepted
- Date: 2026-09-04
- Deciders: команда разработки «Тёплый дом»

## Context

В As-Is одна Postgres на весь монолит ([ADR-003](0003-postgresql.md)). To-Be режем систему по bounded contexts: пользователь/дом, устройства, команды, телеметрия, сценарии. Команда — 5 человек. Нужен независимый деплой и рост телеметрии без остановки отопления. Общая БД снова свяжет сервисы схемой.

## Decision

У каждого микросервиса своя PostgreSQL. Чужую таблицу сервис не читает. Данные другого контекста — только через его API или событие в брокере.

Scope: To-Be. Монолит до выноса продолжает свою одну БД.

## Alternatives considered

- Одна общая Postgres на все сервисы — проще на старте, но деплой и схема снова общие; граница контекста останется только на бумаге.
- Разные движки сразу (Postgres + Mongo + Timescale) — команда не оперировала этим в проде, выигрыша на 100 домов нет.

## Consequences

- Positive: сервис можно выкатить отдельно; телеметрия не душит реестр устройств; совпадает с 12-factor «backing service».
- Negative: нет JOIN «дом + датчик + показание» в одном SQL; нужны API или read-модель, если отчёт склеит три контекста.
- Follow-up: контракты в задании 4; при выносе из монолита копировать данные своего контекста, не открывать монолиту чужие таблицы.
