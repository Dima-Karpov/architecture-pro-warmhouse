# ADR-007: Личность в user-house, проверка доступа в Gateway

- Status: Accepted
- Date: 2026-09-04
- Deciders: команда разработки «Тёплый дом»

## Context

SaaS: жилец сам заходит и трогает только свои дома. Без проверки любой вызов в `command` или `telemetry` — чужой котёл. Команда — 5 человек. Отдельный Keycloak / auth-сервис — ещё один деплой и контур, которого нет в задании 6.

У жильца несколько домов ([ADR-008](0008-user-house-membership.md)). Токена с одним `house_id` мало.

## Decision

Кто такой пользователь — в `user-house`: регистрация, логин, дома, членства, выдача токена.

Доступ = членство, не «хозяин». Токен несёт только `user_id`. Клиент шлёт `house_id` (header/body); Gateway проверяет членство; `command` сверяет `device.house_id`.

`device`, `command`, `telemetry`, `scenario` логин не делают. Они доверяют Gateway и проверяют только своё: устройство дома, в котором жилец состоит.

Отдельный микросервис авторизации не заводим.

## Alternatives considered

- Auth-сервис + IdP — правильно для большой платформы; для 100 домов и пяти человек лишняя операционка.
- Каждый сервис сам ходит в БД пользователей — снова общая схема, ломает [ADR-004](0004-db-per-service.md).
- `house_id` в токене — ломается, когда домов несколько; `house_id` шлёт клиент (header/body).
- Без авторизации — нельзя self-service и несколько домов.

## Consequences

- Positive: один вход для жильца; сервисы проще; resident и второй owner не равны чужому жильцу.
- Negative: Gateway — точка отказа на все вызовы жильца; внутренний вызов `scenario` → `command` идёт без браузера — там своя служебная доверенность, не токен жильца.
- Follow-up: задание 4 — логин и проверка членства; в MVP задания 6 можно заглушку токена, контракт тот же.
